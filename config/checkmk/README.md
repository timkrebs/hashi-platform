# Checkmk configuration

Everything on the cluster side is declarative — the collectors in `gitops/`, the
IAM and log group in `infra/`, the Vault AppRole in `config/vault/`. This
directory is the part that is not: **there is no Terraform provider for
Checkmk** (verified against the registry: `provider not found`), so the site's
own configuration is done through its REST API or the UI.

Checked against the running site: Checkmk **2.4.0p36**, edition **cre** (Raw),
site `cmk`. All four rulesets used below exist in that edition:

| Ruleset | Used for |
| --- | --- |
| `active_checks:httpv2` | Vault health, no token required |
| `special_agents:kube` | Kubernetes cluster, nodes, workloads |
| `special_agents:prometheus` | Vault telemetry, needs an AppRole token |
| `active_checks:cert` | Certificate expiry, optional |

## 0. Teach the site to trust the Vault CA

Both Vault checks talk to a certificate signed by the in-cluster CA, which the
Checkmk host does not know either. Copy it once:

```sh
INSTANCE=$(aws ec2 describe-instances --region us-east-1 \
  --filters 'Name=tag:Name,Values=hashi-platform-dev-checkmk' \
            'Name=instance-state-name,Values=running' \
  --query 'Reservations[0].Instances[0].InstanceId' --output text)

aws ssm start-session --region us-east-1 --target "$INSTANCE"
# on the host:
sudo tee /usr/local/share/ca-certificates/vault-ca.crt > /dev/null   # paste config/vault/vault-ca.pem
sudo update-ca-certificates
```

Skipping this is possible — every check below can disable certificate
validation individually — but then nothing verifies that the Vault answering is
the real one.

## 1. Vault health

The cheapest useful check and the one to add first. `/v1/sys/health` needs no
credential, and its status code already encodes the state:

| Code | Meaning |
| --- | --- |
| 200 | initialised, unsealed, active |
| 429 | unsealed, standby — normal for two of the three pods |
| 473 | performance standby |
| 501 | not initialised |
| 503 | sealed |

In *Setup → Hosts*, create a host `vault` with IP address
`k8s-vault-vaultui-820cb1d6e6-8cab095ee19df462.elb.us-east-1.amazonaws.com` and
**Checkmk agent: No agent** — nothing is installed on those pods.

Then *Setup → HTTP, TCP, Email → Check HTTP web service* (`active_checks:httpv2`):

- **URL** `https://k8s-vault-vaultui-820cb1d6e6-8cab095ee19df462.elb.us-east-1.amazonaws.com:8200/v1/sys/health`
- **Expected status codes** 200, 429, 473
- **Server name indication** `vault.vault.svc.cluster.local` — the certificate
  does not carry the load balancer name, exactly as in `config/vault`
- Assign it to the `vault` host

A sealed or uninitialised Vault then answers 503 or 501 and the service goes
critical.

## 2. Kubernetes

`special_agents:kube` needs both endpoints and a token.

The service account to use is **`checkmk-checkmk`** — the chart binds it to the
`checkmk-checkmk-metrics-reader` cluster role. The other three service accounts
in that namespace belong to the collectors themselves.

```sh
kubectl create token checkmk-checkmk -n checkmk-monitoring --duration=8760h
```

Create a host `hashi-platform-dev-cluster`, again with no agent, then
*Setup → Agents → Kubernetes*:

- **Cluster name** `hashi-platform-dev-cluster`
- **Token** the one just created, stored as a Checkmk password
- **API server** `https://85190A797A1089C3A0B6A4F31FC44422.gr7.us-east-1.eks.amazonaws.com`,
  certificate validation off — the EKS API uses its own CA
- **Cluster collector**
  `http://k8s-checkmkm-checkmkc-75b08705cc-7364897bc7e1e272.elb.us-east-1.amazonaws.com:8080`
- **Collect** nodes, deployments, daemonsets, statefulsets, pods

The collector answers `401` without that token — it validates it through the
Kubernetes TokenReview API — so the internal load balancer is a second layer
rather than the only protection.

## 3. Vault telemetry

Only worth doing once "is it up and unsealed" is not enough any more.

`special_agents:prometheus` against
`https://<vault>:8200/v1/sys/metrics?format=prometheus`, authenticated with the
AppRole from `config/vault`:

```sh
terraform -chdir=config/vault output -raw checkmk_approle_role_id
# secret id, created out of band so no long-lived credential lands in state:
vault write -f auth/approle/role/checkmk/secret-id
```

Log in with both to obtain a token, and store that token in Checkmk. It is
valid for an hour and renewable, so plan for how it gets refreshed before
relying on this in anger — that is the part this setup does not solve for you.

The endpoint deliberately requires a token: the Vault listener is published
through an internet-facing load balancer, so `unauthenticated_metrics_access`
would put seal state, token counts and request rates on the open internet.

## 4. Activate

Nothing above takes effect until the pending changes are activated —
*Changes → Activate on selected sites*. Then, on the two new hosts, run
*Save & go to service configuration* and accept the discovered services.

## What is deliberately not here

**Logs.** Checkmk alerts on patterns in a file an agent can read; it does not
store or search log history. Container logs go to CloudWatch instead, through
`gitops/apps/fluent-bit.yaml` and the `aws-fluent-bit-cloudwatch` module, with
the log group and its retention owned by Terraform. Searching logs happens in
CloudWatch, alerting on state happens in Checkmk.

**Node operating system metrics.** The Checkmk agent on the EKS nodes
themselves would add CPU, disk and systemd state per node. The container view
from the kube agent already covers most of it, so it is left out until there is
a reason.

## Capacity

The site runs on a `t3.medium` with 4 GB, which the `restrict-compute-size`
policy caps. That is fine for this cluster; if the number of monitored services
grows, a second Checkmk host is the way out rather than a bigger one.
